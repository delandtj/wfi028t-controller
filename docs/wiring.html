WFI-028T Controller Wiring

How the ESP32-C6 replacement controller connects to the heat pump's RS-485 bus. It takes the place of the wired controller: two data wires from the controller cable go to an isolated RS-485 module, and four jumper wires join that module to the ESP32-C6 board.

MCUESP32-C6-DevKitC-1 TransceiverRS-485, isolated, automatic direction (no DE/RE) Heat pumpWFI-028T / 035T, 380-415 V 3N

Schematic

The dashed line is the module's galvanic isolation. Nothing crosses it except through the module itself.

3.3 V supply logic ground receive (to GPIO4) transmit (from GPIO5) RS-485 pair

Connections

Six wires in total. The module's TTL side is powered from the board, so the module needs no supply of its own.

Before you power it

One master on the bus

Unplug the stock wired controller before this controller takes over. Two masters on one RS-485 pair corrupt each other's frames. Keep the stock controller as a fallback, never both connected.

Keep the isolation

Do not connect the bus ground (black, 0 V) to the ESP32 ground. The module is galvanically isolated; a ground link defeats it.

A and B

On the reference unit green goes to terminal A and yellow to terminal B. Module markings vary between makers: if the bus reads as 7f, fe or ff garbage, swap the green and yellow wires at the module.

RXD and TXD

TTL-side labelling varies between modules. If the bus stays silent with A and B correct, swap the jumpers on GPIO4 and GPIO5.

Power

A 5 V USB-C charger on the port labelled "USB" is enough. That same port is used to flash the firmware the first time.

A loose GPIO4 looks like silence

An unconnected receive line reads as an idle bus, not as an error. If nothing at all arrives, check that jumper first.

Build the firmware

Plain stable Rust, no ESP-IDF install and no nightly. Tested with Rust 1.98 and espflash 4.6 on Linux.

1

Install Rust

From rustup.rs. If Rust is already installed, rustup update stable is enough.

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
rustup update stable
2

Add the ESP32-C6 target

The C6 is a RISC-V core. The target ships prebuilt, so this is a download, not a compile.

rustup target add riscv32imac-unknown-none-elf
3

Install espflash and get access to the serial port

espflash writes the board over its USB port; on Linux it needs the udev headers to build and your user needs access to /dev/ttyACM*.

Debian / Ubuntu 
sudo apt install pkg-config libudev-dev
sudo usermod -aG dialout $USER
cargo install espflash --locked
Arch 
sudo pacman -S pkgconf systemd-libs
sudo usermod -aG uucp $USER
cargo install espflash --locked
macOS / Windows 
cargo install espflash --locked

No extra packages or groups needed.

Log out and back in after the group change.

4

Get the source

git clone https://github.com/delandtj/wfi028t-controller.git
cd wfi028t-controller

Everything else, including the shared Modbus sniffer core, is fetched by cargo on the first build.

5

Make your own update key

Network updates are only accepted when signed with the key whose public half is built into the firmware. The repository carries the author's public key; make your own pair, or you will not be able to update your board over WiFi. The private key goes to ~/.config/wfi028t/ota-signing.key. Back it up.

mv fw/ota-signing.pub fw/ota-signing.pub.upstream
cargo run -p fw-ota -- keygen
6

Set your WiFi name and password

The board has no setup page yet: the WiFi network name (SSID) and password are built into the firmware. Put them in .cargo/config.toml at the top of the repository, next to fw/. Create the file if it does not exist. That folder is in .gitignore, so the password never ends up in git, and cargo picks it up for every build and flash from fw/.

# wfi028t-controller/.cargo/config.toml  (local only, git-ignored)
[env]
SNIFFER_WIFI_SSID = "your-network"
SNIFFER_WIFI_PASS = "your-password"
# optional, for Home Assistant:
MQTT_HOST = "192.168.1.10"
MQTT_USER = "ha"
MQTT_PASS = "secret"

Changing them later means building and flashing again (over WiFi works, as long as the old network is still reachable). The network must be 2.4 GHz: the ESP32-C6 cannot see 5 GHz. MQTT can also be set later from the console with mqtt host <ip> without a rebuild.

SettingNeededMeaning
SNIFFER_WIFI_SSIDyes2.4 GHz network to join. Without it the board runs with WiFi off (cyan LED).
SNIFFER_WIFI_PASSyes, unless openWPA/WPA2 password.
MQTT_HOSTnoBroker IPv4 address, for Home Assistant.
MQTT_PORTnoDefault 1883.
MQTT_USER, MQTT_PASSnoBroker login.

The same names also work as one-off environment variables, e.g. SNIFFER_WIFI_SSID=... cargo build --release; the config file just saves typing them each time.

7

Build

cd fw
cargo build --release

The first build downloads and compiles the dependencies and takes a few minutes; later builds take seconds.

Flash it

The first flash goes over USB and installs the update layout: a rollback bootloader, two app slots and the firmware. Every later update can go over WiFi.

1

Connect the board

Use a data-capable USB-C cable on the port labelled USB (not "UART"). It appears as /dev/ttyACM0 on Linux, a /dev/cu.usbmodem* on macOS, a COM port on Windows.

2

Flash and watch it boot

From fw/, one command builds, flashes the bootloader, the partition table and the app, then opens the serial monitor. With more than one serial device attached, espflash asks which port; ESPFLASH_PORT skips the question.

cd fw
cargo run --release
# several boards attached:
ESPFLASH_PORT=/dev/ttyACM0 cargo run --release

Look for # wifi connected ip=... in the monitor. Leave it with Ctrl+C; the board keeps running.

3

Talk to it

The console listens on TCP port 4001 at the address the monitor printed. Switch to master only after the stock controller is unplugged.

printf 'status\n' | nc 192.168.1.50 4001        # one command, one answer
nc 192.168.1.50 4001                             # live bus view; type commands
mode master                                      # typed in the console
4

Later updates, over WiFi

Signed with your key from build step 5, with the WiFi settings from step 6, checked on the board before anything is written, and rolled back automatically if the new image does not get the bus working within 120 s.

cd fw && cargo build --release
cd .. && cargo run -p fw-ota -- push 192.168.1.50 --wait

Status LED

The board's RGB LED, highest priority first. Every received frame adds a short flash on top.

Red, blinking 1 HzMaster mode and the heat pump does not answer. Check wiring and A/B.
Blue, blinking 2 HzBooting or joining WiFi.
Amber, steadyOn WiFi, no monitoring client connected.
Green, steadyOn WiFi with a monitoring client connected.
Cyan, steadyWiFi not available in this build.
Flash: green / redA frame with a good CRC / a bad frame or UART error.

Check it works

  1. With the stock controller still plugged in and this board in listen mode, the LED flashes green about twice a second: it hears the stock controller's polls and the heat pump's answers.
  2. Unplug the stock controller and switch the board to master (mode master on the console). It listens for 3 s, then starts polling.
  3. The status line shows mode=master link=up with timeouts not climbing. A red blinking LED instead means no answer from the heat pump.
